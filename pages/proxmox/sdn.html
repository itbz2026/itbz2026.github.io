Proxmox SDN

Zones, VNets, VLAN, VXLAN, EVPN und IPAM

Geltungsbereich: Jeweils Proxmox VE oder PBS/Datacenter Manager wie im Artikel angegeben. Befehle auf dem Proxmox-Host ausführen, sofern nicht anders angegeben. Syntax und Funktionen können versionsabhängig sein; lokale Hilfe und offizielle Dokumentation prüfen.
Praxisreferenz

SDN-Konzepte

Proxmox SDN abstrahiert Netzwerksegmente über Zones, VNets und Subnets. Unterstützte Funktionen und Voraussetzungen unterscheiden sich nach VE-Version.

Vor Planung die SDN-Dokumentation der installierten Proxmox-Version prüfen.
SDN-Konfiguration kann Routing und Erreichbarkeit vieler Gäste beeinflussen.
Praxisreferenz

VLAN Zone und VNet

VLAN-basierte SDN-Netze ordnen virtuelle Netze VLANs und physischen Trunks zu. Switchport, Bridge und VLAN-IDs müssen abgestimmt sein.

ip -d link
bridge vlan show
cat /etc/network/interfaces
VLAN-IDs, MTU und Trunk-Erlaubnis Ende-zu-Ende dokumentieren.
Praxisreferenz

VXLAN und EVPN

VXLAN kapselt Layer-2-Netze über Layer 3. EVPN kann Steuerinformationen für Overlay-Netze bereitstellen.

ip -d link
ip route
bridge fdb show
Underlay-Erreichbarkeit, MTU, UDP-Konnektivität und unterstützte SDN-Konfiguration prüfen.
Praxisreferenz

Subnets und IPAM

SDN-Subnets können IP-Bereiche und Gateway-Informationen abbilden. DHCP- und IPAM-Integration abhängig von Design konfigurieren.

IP-Adressplan, DHCP-Server und Routingtabellen abgleichen.
Doppelte IPs und überlappende Netze vermeiden; Änderungen dokumentieren.
Praxisreferenz

SDN-Fehlerdiagnose

Zone/VNet-Status, Node-Konfiguration, Bridge, VLAN, Routing und Firewall prüfen.

ip -br link
ip route
bridge vlan show
journalctl -b -p warning --no-pager
Nach Änderungen SDN-Konfiguration kontrolliert anwenden und Konnektivität aus Management- und Gastperspektive testen.

Erweiterte Administration & Praxis

Zusätzliche Aufgaben für Betrieb, Diagnose und Expertenpraxis.

Erweiterte Praxisreferenz

Underlay vor Overlay testen

Vor VXLAN/EVPN Node-zu-Node-Erreichbarkeit, MTU und Routing verifizieren.

ping -c 4 <PEER_IP>
tracepath <PEER_IP>
ip route get <PEER_IP>
Hinweis: Overlay-Probleme sind häufig Underlay-Probleme. Zuerst physisches Netzwerk prüfen.
Erweiterte Praxisreferenz

SDN-Änderungen kontrolliert ausrollen

Änderungen dokumentieren, in einem Test-VNet validieren und erst danach produktive Segmente ändern.

ip -br link
ip route
bridge fdb show
Hinweis: Managementzugriff und Gastkommunikation von mehreren Nodes testen.
VXLAN / EVPN

Overlay-Fehler systematisch eingrenzen

Bei VXLAN zuerst Underlay-Konnektivität zwischen allen beteiligten Nodes prüfen. Danach MTU, VTEP-Erreichbarkeit, Routing und erst anschließend Overlay-Konfiguration untersuchen.

ip -br address
ip route get <PEER-IP>
ip -d link
bridge fdb show
ping -c 4 <PEER-IP>
tracepath <PEER-IP>
VXLAN fügt Kapselungs-Overhead hinzu. Die erforderliche Underlay-MTU hängt vom Transport und Design ab. Nicht pauschal MTU-Werte übernehmen.
VLAN Troubleshooting

VLAN-Pfad vom Gast bis zum physischen Switch prüfen

Die VLAN-ID muss auf Gast-NIC, VNet/Bridge, Host-Uplink und Switch-Trunk konsistent sein.

ip -d link show
bridge vlan show
bridge link
cat /etc/network/interfaces
ip -s link
Auf dem physischen Switch zusätzlich VLAN-Mitgliedschaft, erlaubte Trunk-VLANs und Port-Channel-Konfiguration kontrollieren. Management-VLAN vor Änderungen absichern.
Änderungsmanagement

SDN-Änderungen kontrolliert anwenden

Vor dem Apply Konfiguration exportieren bzw. dokumentieren, betroffene Nodes und Gäste identifizieren und einen lokalen oder Out-of-Band-Zugriff sicherstellen.

pvesh get /cluster/sdn
ip -br link
ip route
bridge vlan show
journalctl -b -p warning --no-pager
Achtung: SDN-Konfigurationsänderungen können die Managementverbindung unterbrechen. Keine Netzwerkänderung ausschließlich über die Verbindung durchführen, die dadurch verloren gehen könnte.
Betriebssicherheit: Destruktive Änderungen an Storage, Netzwerk, Cluster oder Gastkonfiguration nur mit geprüftem Backup, Wartungsplan und Rückweg durchführen.
